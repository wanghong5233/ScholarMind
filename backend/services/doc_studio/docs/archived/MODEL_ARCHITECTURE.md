## 一、Agent 架构分析

### 1.1 当前架构

```
┌─────────────────────────────────────────────────┐
│            LaTeX Edit Agent                      │
├─────────────────────────────────────────────────┤
│                                                 │
│  1. Planner（规划器）                            │
│     └─> _llm_reason_and_act()                  │
│         • 理解用户意图                           │
│         • 分解任务                               │
│         • 选择工具（tool_name）                  │
│         • 生成参数（parameters）                 │
│         ⚠️ **需要 LLM** - 这是微调目标           │
│                                                 │
│  2. Executor（执行器）                           │
│     └─> tool.execute()                         │
│         • 直接调用工具（确定性操作）              │
│         • 工具内部可能有 LLM（如检索、分析）      │
│         ✅ **不需要微调**                        │
│                                                 │
│  3. Reflector（反思器）                         │
│     └─> _reflect()                              │
│         • 简单规则判断（当前实现）                │
│         • 可选：用 LLM 做深度反思                │
│         ⚠️ **可选 LLM**（当前不需要）            │
│                                                 │
└─────────────────────────────────────────────────┘
```

### 1.2 关键发现

**✅ Planner 是唯一需要微调的部分**

- **任务明确**：根据观察选择工具和参数，这是结构化决策
- **7B 足够**：工具选择是分类任务，不需要复杂推理
- **资源友好**：只微调一个模型，训练成本低
- **效果明显**：优化 Planner 直接提升 Agent 整体性能

## 二、模型分工策略

### 2.1 微调模型：Planner（7B）

**职责**：
- 理解用户意图
- 分解任务
- 选择工具（从 10 个工具中选择）
- 生成工具参数（JSON 格式）

**模型选择**：
- **Base Model**: Qwen-7B-Chat 或 LLaMA-2-7B-Chat
- **微调方式**: LoRA/QLoRA（参数高效微调）
- **参数量**: 7B（适合学生资源）
- **部署方式**: 本地部署（单卡 GPU）

**资源需求**：
- 训练：单卡 A100 (40GB) 或 2x RTX 3090 (24GB)
- 推理：单卡 RTX 3090 (24GB) 或 A100 (40GB)
- 模型大小：~14GB (FP16) + 100MB (LoRA)

### 2.2 API 模型：工具内部（按需调用）

**职责**：
- 工具内部需要复杂推理时调用
- 例如：`analyze_context_tool` 可能需要 LLM 分析文本语义

**模型选择**：
- **API 模型**: Qwen-Plus / GPT-4（大模型，按需调用）
- **使用场景**: 复杂文本分析、语义理解
- **成本控制**: 只在需要时调用，不频繁调用

**为什么不需要微调？**
- 工具内部 LLM 调用是辅助性的
- 主要决策由 Planner 完成
- 大模型 API 已经足够好，不需要微调

### 2.3 规则系统：Reflector（当前实现）

**职责**：
- 检测工具执行错误
- 决定是否需要修复

**当前实现**：
- 简单规则判断（不需要 LLM）
- 如果工具失败，触发反思

**未来可选**：
- 可以用小模型（1-3B）做深度反思
- 但当前简单规则已经足够

## 三、微调策略总结

### 3.1 微调目标

**只微调 Planner（规划器）**

```python
# 微调前：使用 API 模型
planner = LLMClient(api_model="qwen-plus")  # API 调用

# 微调后：使用本地 7B 模型
planner = PlannerModel(model_path="models/latex_planner_rl")  # 本地部署
```

### 3.2 模型对比

| 组件 | 微调前 | 微调后 | 说明 |
|------|--------|--------|------|
| **Planner** | Qwen-Plus API | Qwen-7B (微调) | ✅ 微调目标 |
| **工具内部** | Qwen-Plus API | Qwen-Plus API | ⚠️ 保持 API |
| **Reflector** | 规则系统 | 规则系统 | ✅ 不需要 LLM |

### 3.3 资源对比

**微调前（纯 API）**：
- 成本：每次调用 ~$0.01-0.1
- 延迟：~1-3 秒
- 资源：无本地资源需求

**微调后（Planner 本地）**：
- 成本：本地部署，无 API 成本
- 延迟：~0.5-1 秒（本地推理更快）
- 资源：单卡 GPU（RTX 3090/A100）

## 四、关于 Qwen-Plus

### 4.1 Qwen-Plus 是什么？

- **类型**: API 模型（阿里云 DashScope）
- **参数量**: 未公开（可能是 72B+）
- **用途**: 通用大模型，不适合微调

### 4.2 为什么不用 Qwen-Plus 微调？

1. **参数量太大**：72B+ 参数，学生资源无法支持
2. **API 模型**：不提供模型权重，无法微调
3. **成本高**：即使能微调，训练成本极高

### 4.3 推荐方案

**使用开源 Qwen-7B**：
- ✅ 参数量：7B（适合学生资源）
- ✅ 开源：提供模型权重，可以微调
- ✅ 性能：7B 模型对工具选择任务足够
- ✅ 成本：LoRA 微调只需训练 1-2% 参数

## 五、实施建议

### 5.1 第一阶段：使用 API（快速验证）

```python
# 使用 Qwen-Plus API 作为 Planner
planner = LLMClient(api_model="qwen-plus")
```

**优点**：
- 快速验证 Agent 功能
- 无需本地资源
- 收集训练数据

### 5.2 第二阶段：微调 Planner（优化性能）

```python
# 微调 Qwen-7B 作为 Planner
planner = PlannerModel(model_path="models/latex_planner_rl")
```

**优点**：
- 本地部署，响应更快
- 无 API 成本
- 针对任务优化

### 5.3 第三阶段：持续优化（可选）

- 收集更多训练数据
- 迭代微调模型
- A/B 测试对比效果
